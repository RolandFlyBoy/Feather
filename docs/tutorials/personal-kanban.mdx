This is the longest part of the series, because authentication, cloud storage and the
admin panel arrive together.

Most of that surface is already built. Google sign-in, the approval workflow, a user admin
panel with analytics and error logs, and a storage interface are scaffolded or provided, so
the prompt below is mostly asking for your domain model on top of them.

Sort your credentials out first. Nothing here runs without them.

## What you'll have

- Google sign-in, with new accounts held for approval
- A dashboard listing your boards, and multiple boards per user
- Roles doing real work: editors and admins can change things, everyone else reads
- The admin panel at `/admin/` for approving and promoting users
- PDF attachments on cards, stored in Google Cloud Storage
- A board exported to PDF on demand

## Step 1: Credentials

| Credential | Where | What you need |
| --- | --- | --- |
| **PostgreSQL** | `brew install postgresql` | A local server running |
| **Google OAuth** | [Cloud Console credentials](https://console.cloud.google.com/apis/credentials) | Client ID and secret |
| **GCS bucket** | [Cloud Storage](https://console.cloud.google.com/storage/browser) | A bucket name |
| **Service account** | [IAM service accounts](https://console.cloud.google.com/iam-admin/serviceaccounts) | A JSON key |

<AccordionGroup>
  <Accordion title="Google OAuth setup" icon="key-round">
    1. Open [APIs and Credentials](https://console.cloud.google.com/apis/credentials).
    2. Create an OAuth 2.0 Client ID of type **Web application**.
    3. Add `http://localhost:5173/auth/google/callback` as an authorized redirect URI.
    4. Copy the client ID and secret.
  </Accordion>
  <Accordion title="GCS setup" icon="hard-drive">
    1. Create a bucket in [Cloud Storage](https://console.cloud.google.com/storage/browser).
    2. Create a service account in [IAM](https://console.cloud.google.com/iam-admin/serviceaccounts).
    3. Grant it the **Storage Object Admin** role.
    4. Create a JSON key and copy the entire contents.
  </Accordion>
</AccordionGroup>

## Step 2: Scaffold

This part needs a different app type, so start fresh.

```bash
feather new kanban
```

Four answers matter:

| Prompt | Answer | Why |
| --- | --- | --- |
| App type | `single-tenant` | You need user accounts |
| Database | `postgresql` | Defaults to sqlite, so type it |
| Redis caching | `n` | Defaults to yes, and nothing here uses the cache |
| Cloud storage (GCS) | keep the default yes | Attachments need it |
| Admin email | the Gmail you'll sign in with | `seeds.py` grants it the admin role |

```bash
cd kanban
source venv/bin/activate

feather db migrate -m "Initial migration"
feather db upgrade
python seeds.py
```

```bash .env
GOOGLE_CLIENT_ID=your-client-id
GOOGLE_CLIENT_SECRET=your-client-secret

GCS_BUCKET=your-bucket-name
GCS_CREDENTIALS_JSON={"type":"service_account","project_id":"...","private_key":"..."}
```

<Warning>
  `GCS_CREDENTIALS_JSON` has to be the whole JSON key on one line. Copy it out of the
  downloaded file and strip the line breaks, or uploads fail against the bucket with an
  error that doesn't obviously point back here.
</Warning>

## Step 3: Run the first prompt

Two prompts, because asking for auth, storage and export in one go is asking for too much.
The first gets you a working app behind sign-in.

```text Prompt 1 of 2: auth and boards
I'm working through part 4 of the Feather Kanban tutorial series.

Read the tutorial first:
https://github.com/RolandFlyBoy/Feather/blob/main/tutorials/04-personal-kanban.md

I've scaffolded a fresh single-tenant app on PostgreSQL with GCS storage
enabled and Redis caching disabled. Migrations have run and seeds.py
created my admin user. GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET,
GCS_BUCKET and GCS_CREDENTIALS_JSON are all set in .env.

Build the authenticated app from Build Steps 0 through 5, stopping
before attachments and PDF export:

- Remove the scaffolded demo home page, its template, its test and the
  counter island. The test goes with the route it tests.
- Kanban, Column and Card models, where a board belongs to a user and
  columns belong to a board. Keep the existing Log, Account and
  AccountUser imports in models/__init__.py, and watch the import order,
  because Alembic creates tables in that order and the foreign keys
  depend on it.
- Services for board, column and card. Editors and admins can create,
  delete and move; everyone else gets read-only. Check ownership by
  walking the relationship (card.column.kanban.user_id), never by
  trusting an ID from the request.
- A dashboard route listing the user's boards, a board route, and the
  move API route.
- Templates for login, pending approval, the dashboard grid and the
  board.

Use @auth_required for pages that need an approved user, and @login_only
for the pending page, since a pending user is authenticated but not
active. Gate the create and delete controls in the templates on
current_user.role, so a read-only user never sees a button that would
fail.

Show me the migration before applying it. Then run `feather check` and
fix what it reports.

Then explain how a brand new Google account moves from first sign-in to
seeing a board, and which decorator or field gates each step.
```

## Step 4: Run the second prompt

Once sign-in works and boards render, add the files and the export.

```text Prompt 2 of 2: attachments and export
Continuing part 4 of the Feather Kanban tutorial.

Sign-in works, the dashboard lists boards, and the board view works with
drag-and-drop.

Now build Build Steps 6 through 9 from the same tutorial:

- PDF attachments on cards, stored through feather.storage. Reject
  anything that isn't a PDF, and delete the previous attachment before
  writing a new one.
- An upload modal and a PDF viewer modal, using the modal component
  rather than a new dialog implementation.
- PDF export of a whole board with WeasyPrint, returned as a download.
- Confirm the OAuth redirect URI configuration.

Use get_storage() rather than talking to GCS directly, so the same code
still works if I switch STORAGE_BACKEND to local.

Then run `feather check` and confirm the checkpoint in the tutorial.

Finally, tell me where the uploaded file actually lives and what would
change if I set STORAGE_BACKEND=local.
```

## Step 5: Test it

```bash
feather dev
```

1. Sign in with Google. A brand new account should land on the pending page.
2. Approve yourself from `/admin/users` as the admin created by `seeds.py`.
3. Create a board from the dashboard, then open it and add columns and cards.
4. Go back and create a second board. Both should be listed.
5. Attach a PDF to a card, then open it in the viewer.
6. Click **Export PDF** and check the download.
7. Open `/admin/` and confirm the user list and analytics render.

Then check the roles behave. Set a second account to the plain `user` role from
`/admin/users` and confirm it sees the boards with no create, edit or delete controls.

```bash
feather check
```

## What the framework did

**You wrote no sign-in code.** Google OAuth, the session, the callback and the user record
are all Feather's. What the prompt asked for was the domain model on top. See
[Authentication](/features/authentication).

**The approval gate is two fields.** A user is pending when `active` is false and
`approved_at` is null, and `@auth_required` raises `AccountPendingError` for them, which
redirects to the pending page instead of returning a bare 403. That's why the pending page
itself uses `@login_only`. See [Exceptions](/backend/exceptions).

**The admin panel is your code.** It was scaffolded into `routes/pages/admin.py` and
`templates/pages/admin/`, so you can change any of it. See
[Admin panel](/features/admin-panel).

**Uploads went through a storage interface.** `get_storage()` returns the configured backend,
which is why the same code works against the local filesystem. Script-capable extensions
are refused by default, which is a real protection given files are served from your own
origin. See [File storage](/features/file-storage).

**Authorization ran twice, on purpose.** The service refuses the action and the template
hides the button. Either alone is a bug: service-only shows controls that fail,
template-only is trivially bypassed.
