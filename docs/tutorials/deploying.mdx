Everything so far ran on your laptop. This part puts it on the internet properly: your
domain, a real certificate, a database that gets backed up, and a deploy that runs on a
merge to `main`.

It's about €7 a month, on one machine. The app, Postgres, Redis and TLS termination all
share the box, and the deployment is eight files `feather new` already put in your
repository.

This part splits differently from the others. The repository work is a prompt like any
other. The server work is a set of commands you run yourself, and the prompt is told not
to touch them.

## What you'll have

- The app at `https://your-domain`, with a certificate that renews itself
- A deploy script that migrates once, swaps containers and waits for health
- Nightly database dumps with retention
- A GitHub Actions workflow that tests, then deploys, on every push to `main`

## Step 1: What you need

- A working app from part 4 or part 5
- A domain whose DNS you control
- A VPS you can SSH into as root. Two vCPU and 4 GB is enough to start
- Docker locally

Check whether the deployment files are already there:

```bash
ls Dockerfile docker-compose.yml docker-compose.dev.yml deploy/
```

If that errors, add them. It never overwrites an existing file.

```bash
feather docker init --domain kanban.example.com
```

## Step 2: Run the prompt

This covers the repository side and prepares the commands you'll run on the server.

```text The prompt
I'm working through part 6 of the Feather Kanban tutorial series.

Read the tutorial first:
https://github.com/RolandFlyBoy/Feather/blob/main/tutorials/06-deploying.md

My app is the result of part 5 and runs locally with `feather dev`. My
domain is kanban.example.com and my server is a fresh Ubuntu 24.04 box
at <IP>.

Do the repository-side work only. Do not SSH anywhere and do not run
anything against the server.

1. Run `feather docker init --domain kanban.example.com` and tell me
   what it generated and what it skipped.
2. Walk me through the generated Dockerfile. I specifically want to
   understand why feather installs on its own layer before the rest of
   requirements.txt, and why there is no `feather db upgrade` in CMD.
3. Bring Postgres and Redis up locally with docker-compose.dev.yml, run
   my migrations against them, and confirm `feather dev` still
   hot-reloads.
4. Build the production image and run `feather security-check` inside
   it. Fix what it reports that is fixable in the repo, and list what I
   have to fix on the server.
5. Write .github/workflows/deploy.yml from Step 8 of the tutorial: a
   test job using real Postgres and Redis service containers, running
   `feather db upgrade`, `feather check` and `feather test`, then a
   deploy job that SSHes in and runs ./deploy/deploy.sh --pull. Include
   the concurrency block so a deploy is never cancelled mid-migration.

Then give me the server commands as a numbered list I can work through
myself: DNS, the deploy user, Docker, the firewall, SSH hardening, the
clone, and the production .env. For each one tell me what it does and
how I know it worked. Flag anything that would lock me out if I get it
wrong.
```

## Step 3: Set up the server yourself

Work through the list the prompt gave you. Two things are worth stating here because
getting them wrong is expensive.

<Warning>
  **DNS before anything else.** Caddy asks Let's Encrypt for a certificate the moment it
  starts, and Let's Encrypt checks the name resolves to the machine asking. Confirm with
  `dig +short kanban.example.com` before you deploy.
</Warning>

<Warning>
  **Keep a second terminal open while hardening SSH.** After you set `PermitRootLogin no`
  and `PasswordAuthentication no` and restart ssh, confirm `ssh deploy@<ip>` works in the
  second terminal before closing the first. Otherwise you've locked yourself out of your
  own server.
</Warning>

The production `.env` is the one file that never enters git and never goes into the image.
At minimum it needs `DOMAIN`, `POSTGRES_PASSWORD`, `SECRET_KEY`, your Google credentials,
`OAUTH_CALLBACK_URL` and `TRUSTED_HOSTS`. Leave `FLASK_CONFIG`, `DATABASE_URL`,
`REDIS_URL` and `JOB_BACKEND` out of it, because compose sets those on the container and a
duplicate is one more thing to disagree.

```bash
feather env check
```

Then deploy:

```bash
./deploy/deploy.sh
```

## Step 4: Test it

1. `https://your-domain` loads over a valid certificate.
2. Sign in with Google. If this works, your proxy headers are right.
3. `curl https://your-domain/health` returns healthy, including the database check.
4. Push a commit to `main` and watch the workflow test, then deploy.
5. Run `./deploy/backup.sh`, then restore the dump into the database.

Then the gate before you tell anyone the URL:

```bash
feather security-check --env-file .env
feather env check
```

## Step 5: The pre-launch review

Worth a second prompt once it's live.

```text Pre-launch review prompt
The app is deployed at https://kanban.example.com and responding.

Work through the pre-launch checklist in Step 9 of the tutorial and the
one at
https://docs.featherframework.org/deployment/checklist.

For each item, tell me how to verify it rather than assuming it. Where
you can check from the repository, check it. Where it needs a command on
the server, give me the command and tell me what a passing result looks
like.

Flag anything that looks wrong, particularly TRUSTED_HOSTS,
OAUTH_CALLBACK_URL and JOB_SERIALIZER.
```

<Warning>
  Keep the assistant off your production server unless you've decided otherwise
  deliberately. Having it prepare commands you run yourself costs almost nothing and keeps
  a review step in front of the script that applies migrations.
</Warning>

## What the framework did

**Migrations ran exactly once, before the swap.** `deploy/deploy.sh` runs
`feather db upgrade` in a throwaway container built from the new image, while the old
containers are still serving. A failed migration stops the deploy and leaves the site up.
It's also why `CMD` doesn't run migrations: two web containers starting together would both
begin the same Alembic upgrade, and Alembic doesn't arbitrate that.

**Healthy means the database is reachable.** The container healthcheck curls `/health`,
which Feather registers and which checks the database rather than just confirming Python is
alive. That's what makes the deploy's health gate worth having. See
[Health checks](/features/health-checks).

**TLS has no cron job.** Caddy obtains and renews certificates for every hostname in the
Caddyfile. What does need attention is `X-Real-IP`: Caddy sets `Host` and
`X-Forwarded-Proto` by default, but not that one, and rate limiting reads it. The generated
config adds it, and deleting that line makes every request look like it came from the same
address.

**CI holds no application secrets.** The server builds its own images, so the workflow
needs two repository secrets and no registry. Your `.env` never leaves the box. See
[Continuous deployment](/deployment/ci-cd).

## Where to go next

- **A staging host.** A second A record, a second checkout, a second compose project name,
  and the same scripts.
- **Log aggregation.** The app writes JSON logs in production. Ship them somewhere you can
  search.
- **Error alerting.** `/admin/logs` records exceptions. Notify yourself when the rate
  spikes.
- **Off-site backups.** A dump on the same disk as the database isn't a backup.
