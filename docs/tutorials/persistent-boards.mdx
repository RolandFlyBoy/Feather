The board from part 1 forgets everything when you reload. This part gives it a database
and makes the buttons work, and almost none of that involves JavaScript.

Creating and deleting cards is the kind of interaction that usually pulls in a client-side
framework. HTMX handles it by requesting a fragment of HTML from the server and swapping
that fragment into the page, which keeps the logic in Python.

## What you'll have

- Columns and cards stored in SQLite
- Create and delete for both, with no page reload
- A confirmation step before anything is destroyed
- Data that's still there after a refresh

## Step 1: Scaffold

<Tabs>
  <Tab title="Continue from part 1">
    Part 1 had no database, so the app has no `models/` package, no `migrations/` directory
    and no `DATABASE_URL`. Add them:

    ```bash
    cd kanban
    source venv/bin/activate

    echo 'DATABASE_URL=sqlite:///kanban.db' >> .env

    mkdir -p models
    cat > models/__init__.py <<'PY'
    """SQLAlchemy models - Auto-discovered by Feather."""

    from feather.db import db, Model
    PY

    feather db init
    ```

    <Note>
      `feather db init` exists for exactly this case. In an app scaffolded with a database
      it fails, because `migrations/` is already there.
    </Note>
  </Tab>
  <Tab title="Start fresh">
    ```bash
    feather new kanban
    ```

    Accept `simple` for the app type, then type `sqlite` at the database prompt. Leave
    background jobs at the default. The prompt below will rebuild part 1's board for you.
  </Tab>
</Tabs>

## Step 2: Run the prompt

```text The prompt
I'm working through part 2 of the Feather Kanban tutorial series.

Read the tutorial first:
https://github.com/RolandFlyBoy/Feather/blob/main/tutorials/02-persistent-boards.md

My app is the result of part 1: a static board with hardcoded columns in
routes/pages/home.py. I've added DATABASE_URL for SQLite, created the
models/ package and run `feather db init`.

Build the persistent board from Build Steps 1 through 7:

- Column and Card models using UUIDMixin and TimestampMixin, with cards
  cascading from their column.
- A migration for them.
- ColumnService and CardService holding the create, delete and list
  logic. Raise NotFoundError for a missing row rather than returning
  None.
- Update the board route to query real data, injecting the services with
  @inject.
- Partial templates for a column and a card, which are what the HTMX
  routes return.
- HTMX wiring: create and delete for both columns and cards, with
  hx-confirm on the destructive ones, and the card form clearing itself
  after a successful submit.
- The new CSS classes.

Conventions from CLAUDE.md that matter here: keep route handlers thin
and put the logic in services, use window.showPrompt() rather than
window.prompt for the "Add Column" dialog, keep JavaScript in static/js/
rather than inline, and keep styles as @apply classes.

Stop before running the migration and show me the generated file. After
I approve it, run `feather db upgrade`, then `feather check`, and fix
anything it reports.

Then walk me through what you built: the models, why the services exist
separately from the routes, and how each HTMX attribute on the board
maps to a route.
```

<Warning>
  The pause before the migration is deliberate. Feather keeps migrations manual so you see
  what Alembic inferred from the models, which matters just as much when an assistant wrote
  them.
</Warning>

## Step 3: Test it

```bash
feather dev
```

1. Click **Add Column** and give it a name. It appears without a reload.
2. Type in the input at the bottom of a column and press Enter. The card appears, and the
   input clears.
3. Hover a card and click the X. Confirm the dialog, and the card goes.
4. Click the X on a column header. Confirm, and the column and its cards go together.
5. Refresh the page. Everything is still there.

```bash
feather check
feather routes
```

`feather routes` is worth a look here. You should see the page route at `/` plus four
`/htmx/` routes, which is everything this part added.

## What the framework did

**The mixins wrote your boilerplate.** `UUIDMixin` gave every row a UUID primary key and
`TimestampMixin` gave it `created_at` and `updated_at`. Neither appears in the model body.
See [Models](/backend/models).

**Deleting a column deleted its cards.** That's `cascade="all, delete-orphan"` on the
relationship. There is no cleanup code in the service.

**The routes stayed thin.** Each handler parses the request, calls a service and returns a
template. A handler doing more than that is reported by
[`feather check`](/tooling/check) as the `fat-route` warning, which is why the logic ended
up in [services](/backend/services).

**A DELETE returns an empty string.** HTMX swaps that emptiness over the element, which is
how the row disappears. A POST returns the rendered partial for the thing it just made.
Both patterns repeat for the rest of the series. See [HTMX](/ui/htmx).

**The confirm dialog isn't the browser's.** `hx-confirm` is backed by Feather's
`confirm_modal` component, so it's styled and dark-mode aware. Native `confirm()` is a
`feather check` error.
