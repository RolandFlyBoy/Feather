Dragging a card is the first thing in this series HTMX can't do well. A drag holds state
for as long as your finger is down, and asking the server about it on every pointer move
would feel awful.

So this is where islands earn their place: a small piece of JavaScript over the board,
updating the UI immediately while the save happens behind it.

## What you'll have

- Columns and cards with stable positions
- Cards you can drag within a column and between columns
- Visual feedback while dragging, and a marker showing where the card will land
- A card that moves instantly and rolls back if the server refuses

## Step 2: Run the prompt

```text The prompt
I'm working through part 3 of the Feather Kanban tutorial series.

Read the tutorial first:
https://github.com/RolandFlyBoy/Feather/blob/main/tutorials/03-drag-and-drop.md

My app is the result of part 2: Column and Card models, services, HTMX create and
delete, and partials for column and card.

Build drag-and-drop from Build Steps 1 through 9:

- Add OrderingMixin to both models. Card needs
  __ordering_scope__ = ["column_id"] so positions run per column rather than across
  the whole table.
- A migration for the position columns.
- Update the services to query in position order, and add a move() method to
  CardService. It has to handle a card crossing between columns, not just
  reordering within one, and close the gap in the column it left.
- An API route under routes/api/ that takes the move as JSON.
- A kanban-board island using the built-in draggable config, with a drag handle.
- data-id on the cards and on the drop zones, and the island mount on the board
  template with its own islands block.
- The drag-drop CSS.

Two conventions matter here. Use this.api from inside the island rather than raw
fetch, so CSRF is handled for you. And use this.optimistic() for the move, so the
card lands immediately and rolls back if the server rejects it.

Show me the migration before applying it. Then run `feather check` and fix
anything it reports, including orphan-island or missing-island.

Then explain two things: why Card needs an ordering scope and Column doesn't, and
what happens in the UI if the API call fails.
```

## Step 3: Test it

```bash
feather dev
```

1. Grab a card by its handle and drag it. The card should dim while it moves.
2. Drop it above or below another card in the same column.
3. Drag one into a different column.
4. Watch it land immediately rather than after a pause.
5. Refresh. The positions held.

Then break it on purpose, because this is the interesting bit:

```bash
# stop the server while the browser is still open, then drag a card
```

The card should snap back where it came from rather than sitting in a position the
database doesn't know about.

```bash
feather check
```

## What the framework did

**Ordering is a mixin, not a column you manage.** `OrderingMixin` brought `position`,
`move_to()`, `insert_at_end()` and `reorder_all()`. The service calls them; nothing
recalculates indexes by hand. See [Models](/backend/models).

**`__ordering_scope__` is the line that matters.** Without it, positions would be unique
across the whole cards table and two columns would fight over them. With it, each column's
cards start again at zero.

**The island didn't call `fetch`.** `this.api` is the CSRF-aware helper, and raw `fetch`
is a [`feather check`](/tooling/check) error, because a POST without the token fails in
production and works in nobody's test. See [Islands](/ui/islands).

**Optimism is a wrapper, not a pattern you implement.** `this.optimistic()` takes the
instant change and the server call, and rolls the first back if the second fails. That's
the rollback you tested above.

**The route returned JSON.** Every other route so far returned HTML because the browser
was going to insert it. Here the island already moved the element and only needs to report
where it landed, so `routes/api/` is the right home. See [Routes](/backend/routes).
